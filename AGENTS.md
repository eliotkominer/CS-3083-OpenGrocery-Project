# OpenGrocery repository guidance

Start with [the project context](docs/project-context.md) and [source inventory](docs/file-inventory.md). This is a two-person NYU Tandon database project comparing grocery prices by branch and complete shopping list. The team reports Parts 1 and 2 submitted. React, Node.js/Express, and a running PostgreSQL-backed application are Part 3 plans.

- Use current instructor announcements for changes, the original Part 1 diagram for conceptual claims, and the submitted SQL in [database/](database/) for the relational baseline. The inventory lists the external course reference PDFs. Keep course PDFs, private identifiers, credentials, and other uploaded references out of the public repository unless the team expressly approves publication.
- Preserve the submitted SQL and demo data in `database/`. The seven tables are `Retailer`, `Store`, `Product`, `"User"`, `ShoppingList`, `PriceRecord`, and `ShoppingListItem`. Keep the double quotes on `"User"`. `Contains` is the ER relationship. Use the submitted DDL for keys, nullability, and constraints. Explain proposed Part 3 changes and their impact on test data before editing.
- Compare the same packaged product at individual stores. Use the latest observation by `observed_at DESC, price_record_id DESC`. Multiply by requested quantity and check coverage before reporting a full-list total. Treat missing prices as unknown.
- Follow the syllabus (pp. 4–6) on student authorship, copying, outsourcing, and the prohibition on AI-assisted code or solutions. Keep assistance within permitted context and organization work. Both students must write substantial code and understand the entire system. Use genuine student evidence for assessed reports.
- Record plans, observed files, and executed checks separately. Verify the current repository, source, and environment before claiming a feature, query, test, demo, or submission succeeded. Capture the command and result for any execution claim.
